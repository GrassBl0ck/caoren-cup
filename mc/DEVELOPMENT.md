# 草人杯 MC 架构与开发说明（审阅稿）

日期：2026-10-31。适用于后续 MC 系统与玩法接入，不改变现有玩法规则。

本文公开已确认的架构边界与待审阅的工程建议，配套新增模块提案使用。具体开发审批与协作操作遵守维护者的本地约定；本文不授予提交、发布或生产操作权限。

## 已确认的开发和运行边界

- 正式修改发生在主仓库 `mc/`，按已确认的分支和协作流程开发；旧的独立 MC 工程目录保留为历史参考，不进行双向业务同步。本轮不搬迁、删除旧目录或设置操作系统只读权限。
- 单玩法限制只约束草人杯外层切图：同一时间仅启用一套玩法/地图，不预留外层多开。第三方小游戏合集按整体接入，内部选择、运行和原有并行能力保持上游方式，不强制全服同一小游戏。
- 一套外层内容可以使用多个地图区域或维度，须列清影响范围；这不代表建立第二个草人杯服务实例，也不根据合集内部游戏数量增加外层调度。
- 草人杯外层只维护当前启用项与切换状态；第三方内部状态继续由上游负责，不套用自研对局流程。自研对局标识仅用于日志、恢复、结算去重和识别旧回调，不引入房间编号、实例池或调度框架。
- 切换玩法按单玩法服务的停止、切换、启动和就绪检查设计。玩家是否需要重连、预计影响及对进行中对局的处理必须在切换方案中说明。
- 自研优先选择插件，数据包作为次选或配合；每个玩法先说明选择理由及两者的职责。第三方内容按原工程及兼容实测单独确定。
- 当前服务端不因写入本规范而升级、更换引擎或改用代理。改变已确认边界须重新提出方案。

## 已确认的目录归属（2026-11-01）

MC 层保留共用规范、工具和资料；专属文件放入具体玩法。第三方小游戏合集整体作为一个玩法文件夹。坐垫战争总目录 `cushion-wars/` 内含 `cushion-wars-a/`、`cushion-wars-b/` 和共用资料 `shared/`。

## 职责划分建议

| 层级 | 负责的内容 | 归属边界 |
|---|---|---|
| 平台共用层 | 草人杯账户、邮箱密码、网站会话与平台权限 | MC 只接入已确认的平台能力；MC 正版身份与网站账户是否强制绑定尚待确认 |
| MC 基础能力 | 消息、权限检查、配置校验、日志和公共接口 | 不包含具体胜负、回合或技能规则；使用共享库还是独立插件，按首个相关任务确认 |
| MC 通用系统 | 地图管理、菜单、单局管理、玩家状态恢复等共用功能 | 通过明确接口协作，不能直接改写另一模块的私有文件或状态 |
| 独立玩法 | 胜负、人数、回合、技能、规则相关数据包 | 具体规则归该玩法；单独 JAR、已有 JAR 内模块或数据包均需逐项确认 |
| 地图与资源 | 世界模板、地形生成、音频、资源版本与下载入口 | 区分正式模板和运行存档，明确工具能够写入的路径 |
| 第三方适配 | 来源、许可、版本、兼容环境、启动与状态适配 | 保留上游边界；不因接入统一菜单而声称兼容所有引擎或获得全部再分发权限 |

这些是职责分类，不是立即创建的目录或插件清单。新增模块先使用 [接入提案](templates/module-proposal.md) 确认具体目标。

现有切图 `/maps` 的实现附在坐垫战争插件中，并会让当前实例玩家断开后停服；现有 `mapctl` 使用不同世界容器但共用插件、权限和日志。通用切图的后续归属需单独确认，本轮不迁移这些实现。

## 新增模块接入建议

### 先明确归属和依赖

- 登记名称、唯一模块标识、负责人、用途、具体 JAR/数据包、目录、命令、权限节点、配置文件及依赖。
- 说明模块属于系统还是玩法，以及启用、停用、缺依赖和配置非法时的表现。未启用的模块不应继续更改玩家、世界或显示可操作菜单。
- 依赖通过公开且有版本约定的接口交互。插件与数据包明确唯一规则主控，避免分别维护两份计分、倒计时或阶段状态。
- 配置声明类型、默认值、范围、何时可修改及恢复办法。网页管理动作使用已定义操作和参数校验；权限由服务端检查。

### 对局开始与结束

对于草人杯自研对局管理，建议统一生命周期含义为“准备、等待、进行、结算、清理、异常待处理”，具体名称和枚举在实现任务中确认。这里的生命周期不同于外层地图切换；玩法内部可以有自己的回合阶段，不强行替换现有枚举，也不据此改造第三方合集内部流程。

| 场景 | 需要明确和验证的结果 |
|---|---|
| 开始 | 配置、地图、依赖及玩家条件验证完成后再进入可比赛状态 |
| 重复开始/停止 | 请求可安全拒绝或重复执行，不叠加倒计时、监听器或结算 |
| 正常结束 | 记录结果，处理已确认的结算，然后清理本局资源 |
| 管理员中止 | 按用户确认的中止规则收尾，不擅自新增判负或奖励逻辑 |
| 切图/停服 | 明确能否中断当前对局、通知范围、保存与恢复顺序；目标失败有受控处理办法 |
| 清理失败 | 保留恢复证据并明确提示，处理完毕前不继续接受下一局 |

延迟任务和异步回调处理前校验所属对局仍有效，避免上一局操作落到下一局。网站不可用时已开启对局如何继续、哪些管理或绑定操作暂停，需在涉及联动的任务中确认。

### 玩家、物品与世界恢复

- 列出会修改的玩家属性：背包、血量、模式、飞行、碰撞、效果、队伍、显示、位置等，逐项说明保存和恢复责任。
- 玩家原状态先可靠保存再修改。恢复记录损坏或无法完成安全传送时保留现场和原记录，避免按空数据清物品。
- 快照恢复需要配合物品边界：检查丢弃、容器、死亡掉落、退出、传送等路径，避免临时物品带出或恢复被重复执行。
- 玩家离线、死亡、复活、重连、插件关闭和进程异常退出均列出处理结果。是否允许回局、替补及如何判负由玩法负责人确认。
- 清理只作用于登记归本模块/本局所有的实体、任务、计分板、队伍、显示和临时世界；世界级规则记录原值及恢复策略。
- 是否保存玩家进度、战绩或奖励由具体需求确定。如有结算，说明持久化、重试去重以及记账/发放中途失败的补偿规则。

### 性能、权限与消息

- 对耗时 I/O、定时任务、实体数量、区块加载及地图构建明确预算和故障处理。后台 I/O 与世界操作分别遵守对应线程要求。
- 延迟以游戏 tick 还是现实时间计算须明确，避免低 TPS 时把倒计时含义弄错。Folia 兼容不是已有承诺，需要另行评估和验收。
- 正版身份以可信登录链路得到的 UUID 为依据，昵称用于显示；网站管理员、玩法管理员和服务器运维权限分别确认，不凭昵称或前端参数授予权限。
- 消息使用统一 `[草人杯]` 前缀及按接收范围确定的颜色；统一工具本身与实际功能输出路径都要核查。
- 后续若拟改变为代理或其他登录链路，先按架构变更重新确认，并核查整个正版验证链路。本规范不为单玩法架构添加代理组件。

## 来源与版本

- `source-manifest.json` 保存原导入来源及字节证据。原版资源固定提交、下载地址和 SHA-256 持续保留；第三方修改保留上游来源、原许可和修改说明。
- 正式开发版本由 Git 提交、组件版本、构建输入和发行清单确定；不能把开发后的内容重新标成未经修改的导入快照。
- `source-manifest.json` 保留导入时路径与哈希；`source-layout.json` 记录当前路径映射及明确登记的引用调整哈希，`verify_sources.py` 校验移动后的文件。后续源码变更继续明确原因和验证记录，不覆盖原导入证据。
- 整体发行版本、各插件/数据包版本、地图资源版本及持久化数据结构版本分别记录，变更说明标出彼此兼容关系。
- 自研 MIT 不覆盖第三方；世界、音频、大资源、依赖缓存、账号、玩家数据、凭据与生产配置按现有策略管理。
- 目前导入的 `CushionWarsProbe` 同时包含探针与玩法，其名称及成熟状态是现状；正式命名、拆分和实验功能启用范围须另行确认。

## 验收建议

新系统或玩法至少写清以下检查中哪些适用、如何执行、哪些尚未通过：

1. 规则/配置测试、编译和数据包或地图结构检查。
2. 正常加入、开始、正常结束与连续两局。
3. 重复操作、人数边界、管理员中止及未授权请求。
4. 断线、重连、死亡、复活、停服及恢复记录损坏。
5. 退出后背包与属性恢复、无重复物品、无残留任务/实体/队伍或世界规则污染。
6. 声明运行环境下的真实客户端验证和必要负载检查。

组件登记为“实验、试玩待验收、稳定”之一，附实际验证证据和未覆盖项。源码收录、构建成功、用户验收、发布及生产部署分别记录。

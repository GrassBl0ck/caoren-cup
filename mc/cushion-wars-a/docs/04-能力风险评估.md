# 能力风险与技术路线评估（未实测）

**性质声明**：本文是基于 26.3 官方发布包静态证据（`references/vanilla-audit/`）与方法签名的**工程判断**，不是测试结果。所有结论都必须由 P0 实测确认或推翻。写下它的目的是：在投入完整玩法层之前，先把“纯数据包能不能做到”这件事讲清楚，避免做完才发现方向不对。

## 1. 判断依据（本地可查）

| 依据 | 位置 | 说明 |
|---|---|---|
| 数据包只有 tick 边界钩子 | `tags/function/tick.json` | 函数不会插入到玩家输入的处理过程中 |
| 坐垫放置流程 | `CushionItem.javap.txt` → `useOn` | 放置与消耗在同一调用内完成并返回 `InteractionResult` |
| 下座判定 | `Player.javap.txt` → `wantsToStopRiding` / `rideTick` | 潜行即请求下座，`rideTick` 内有 `stopRiding` 路径 |
| 箭命中的伤害入口 | `ProjectileUtil.javap.txt`、`Player.javap.txt` → `hurt` | 命中即 `hurt`，受 `invulnerableTime` 约束 |
| 喷溅药水 | `ThrownSplashPotion.javap.txt` | 移动碰撞箱 → 候选框扩张 → 强度衰减 → 瞬时效果 |

## 2. 逐关卡判断

| 关卡 | 判断 | 主要理由 | 可信度 |
|---|---|---|---|
| G01 输入与 AP 门禁 | **严格标准预计不可达** | 原版交互在数据包看到之前已完成；“失败”只能事后回滚，回滚前的 1 tick 已产生有效结果 | 中等，须实测 |
| G02 乘坐与主动下座 | **严格标准预计不可达** | 无法覆写 `wantsToStopRiding`；每 tick 重挂存在空档 | 中等 |
| G03 门与放置 | **部分可达** | “没有门物品”可以从结构上禁止放置；但开门/关门 1 AP 必须先发生再扣费 | 较高 |
| G04 箭矢逐箭伤害 | **预计不可达** | 无法取消 `hurt`，未发现可把箭伤置零的字段；同 tick 多箭被无敌吞掉 | 较高 |
| G05 治疗与同批顺序 | **部分可达** | 原版数值与饮用时长可保留；“先伤害后治疗”依赖接管伤害路径，若不达标则顺序无法保证 | 较高 |
| G06 限定观战 | **严格标准预计不可达** | spectator 自带自由飞行、穿墙、任意切换目标 | 较高 |
| G07 信息隔离 | **可达，但准星部分只能近似** | 分团队 sidebar/actionbar 可行；无原生“准星目标”选择器 | 中等 |
| G08 计时与定向清理 | **可达** | 纯 tick 计数 + 有范围命令；地图层已实现并过 29 项静态校验 | 高 |

## 3. 如果 G04 等确实不通过，可选的替代（都需要你批准）

| 替代 | 做法 | 代价 |
|---|---|---|
| A1 总量补偿 | 允许原版吞伤，事后把差额补上 | 死亡时序与“逐箭独立”的严格语义都不满足；击杀瞬间可能先显示未死 |
| A2 非箭投射物 | 用雪球/自定义追踪实体代替箭，伤害由 `damage` 自算 | 违反“真实原生弓与箭”的表现要求，须你明确同意 |
| A3 伤害重写 | 箭命中后立即 `damage` 并要求不触发原版箭伤 | 目前没有证据表明能把原版箭伤归零 |

## 4. 三条技术路线（请你选一个方向）

### 路线一：纯数据包 + 近似规则（原约束不变）
- 保持 Minecraft 26.3 原版客户端与原版服务端，只改数据包。
- 需要逐条放宽：逐箭独立伤害、禁止下座、准星血量、限定观战。
- 交付形态与本轮一致，但**A-V1.0 的若干条规则会被改写**，需要你逐条确认。

### 路线二：服务端插件（推荐先评估）
- 玩家仍然使用**原版客户端**，只把逻辑从数据包换成服务端插件（如 Paper 26.3 或 Fabric 服务端模组）。
- 能严格实现：交互前置校验、逐箭独立伤害、下座拦截、观战限制、准星判定。
- 代价：安装方式从“丢一个 ZIP 进 datapacks”变成“装服务端与插件”，组织者需要更多准备；这**不改变玩家侧体验**。
- 这是“原版客户端”约束下唯一能满足 A-V1.0 严格语义的方案。

### 路线三：缩范围
- 先只交付地图 + 回合流程 + 原版战斗（伤害走原版规则），把“逐箭独立、固定 6 HP 额外伤害”等自定义战斗规则留到以后。
- 好处是可以较快得到一个能玩的东西；坏处是与你已确认的规则不一致。

## 5. 我的建议

先按 P0 顺序实测 **G04、G02、G01** 三项——它们决定路线。若三项中任意两项判 FAIL，建议直接转向路线二；若只有 G04 不通过而其余可达，可以在路线一与路线二之间按“能否接受伤害补偿”做取舍。

在这三项有实测结论之前，不建议继续写玩法层代码：那部分工作很可能因为底层能力不可用而整体作废。

## 6. 2026-10-25 后续决定（本文写作之后的更新）

用户已选择 **路线二：服务端插件**，具体为 **Paper 26.3 插件**，玩法入口改为“组织者开一个 Paper 服务端，玩家用原版客户端连接”，放弃“纯数据包”这一硬约束。

因此本文第 2 节对 G01/G02/G04/G07 的“预计不可达”结论**只对纯数据包成立**，不再代表当前方案。插件路线下的实际能力与仍需实测的点，改看 `06-Paper插件验证方案.md`：

- 已核实的事实：Paper 26.3 已是 stable（构建 218—223），`api-version` 为 `26.3`，要求 Java 25。
- 已实现并通过编译的探针：`dist/CushionWarsProbe-0.1.0.jar`，覆盖 G01/G02/G04/G07。
- 仍未验证：插件能否在真实服务端加载并达到预期行为——用户本轮未授权启动服务端，P0 依然全部 `NOT_RUN`。

数据包没有作废：M1 地图层（坐标源数据、生成器、29 项几何校验、建图/缩圈/自检函数）继续作为地图与棋盘收缩的实现，插件只负责规则判定。

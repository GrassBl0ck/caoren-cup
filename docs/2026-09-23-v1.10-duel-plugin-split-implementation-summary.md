## 3. 与设计的偏差及理由(已确认的实施决策)

1. **`caoren_bridge_matchid` ConVar 未实现(设计 4.2)**:实测 CSSharp 1.0.367 的 `ConVar` 类只有 `Find`、无创建 API;1.0.374 包不含 net8.0 目标,而设计禁止修改桥接 csproj。改为 `css_duelbridge_begin` **不带参数**,桥接收到通知后直接用自身 `_currentMatchId` 作为 stale ID 传入 `Begin()`——与拆分前 `Begin(_currentMatchId)` 完全等价,同为游戏线程同步派发,无时序竞争。设计第 9 节"观察该 ConVar"改为观察桥接日志(begin 时打印旧比赛 ID)。
2. **通知用 `AddCommand` 而非设计 4.1 的 `AddCommandListener`**:`AddCommand` 注册的真实命令经 `Server.ExecuteCommand` 派发是 CSSharp 跨插件通信的可靠路径;玩家来源由处理器直接拒绝,防伪造效果相同。
3. **桥接保留最小 `DuelControlMode { None, GameManaged }` 枚举**(置于 `WebCommandGameThreadDispatcher.cs`):`WebCommandGameThreadDispatcher` 的 API 以 `Func<DuelControlMode>` 耦合单挑会话,为完全不改该文件及其测试,桥接用 `_duelTelemetryIsolation.IsActive` 映射出"GameManaged 活跃窗口"传入(`CurrentDuelControlModeForWebCommands()`),拦截语义等价且在清理窗口期更严格。
4. 设计第 8 节"6 个专属文件"系笔误,整体迁移实为 5 个(3.1 表为准,`DuelTelemetryIsolationState` 留桥接)。
5. 测试并非全部"整体随迁":`DuelGameSessionTests` 与 `FinalReviewFixTests` 是混合文件,按锚定对象拆分(桥接锚定的留在桥接并适配)。

## 4. 跨插件隔离协议(实际实现)

单挑插件 → 桥接,经 `Server.ExecuteCommand` 同步派发,桥接侧校验仅服务器/控制台来源(玩家执行直接忽略):

| 命令 | 单挑插件触发时机 | 桥接动作(等价拆分前调用) |
|---|---|---|
| `css_duelbridge_begin` | 单挑开始(TryStart 成功后) | `BeginBarrier()` → `Begin(_currentMatchId)` → `_currentMatchId=null` → `ResetLiveMatchStats(0)` |
| `css_duelbridge_cleanup_restart` | 决定清理重启(BeginDuelCleanup / CleanupDuelImmediately) | `BeginBarrier()` → `BeginCleanupRestart()` → `UpdateCvarRestoreReady(false)` → `_duelCvarRestorePending=true` |
| `css_duelbridge_round_start` | 每个 RoundStart(无脑通知,守卫在桥接状态机内) | `CompleteCleanupRoundStart()` → `CommitReleasedDuelHeartbeatStateOnGameThread()` → `DrainDeferredHeartbeatCommandsAsync()` |
| `css_duelbridge_cvar_ready <0\|1>` | CVar 恢复状态每次变化(原 `UpdateCvarRestoreReady` 的全部调用点) | 更新 `_duelCvarRestorePending` → `UpdateCvarRestoreReady(ready)` → Commit → 就绪时 Drain |

时序与拆分前逐条对齐(设计 4.3):释放三条件 = 清理重启后首回合(经 round_start 通知)+ 观察到安全心跳(桥接自行观察)+ CVar 恢复就绪(经 cvar_ready 通知)。桥接单方面缺失时(未部署 CaorenDuel),通知命令成为未知命令,无副作用。

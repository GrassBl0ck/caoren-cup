# 已废弃：草人杯全地图粒子菜单设计（CounterStrikeSharp-only）

> **状态：已废弃，2026-07-22。** 用户已决定使用新版 SwiftlyS2 单独承载粒子菜单；请改读 `2026-07-22-swiftlys2-particle-menu-design.md`。本文件保留用于说明 CounterStrikeSharp-only 输入方案为何停止，不能作为实施依据。

## 目标

在不修改官方地图的前提下，为草人杯 CS2 服务器提供可嵌套、多页面的粒子菜单。菜单使用自定义粒子、材质和图标显示；玩家使用虚拟鼠标选择；菜单开启期间不会转动视角或触发开枪等游戏操作。

## 范围与非目标

- 菜单需要在服务器当前可切换的官方地图和创意工坊地图上可用。
- 菜单作为现有 `game-plugin/` 中的功能模块发布，不新建第四个正式游戏 DLL 或 Release ZIP。
- 菜单专属资源通过独立创意工坊 Addon 分发，不放入普通插件部署包。
- 本设计不包含创意工坊资源的美术制作，也不改变网页端、桌面客户端或现有比赛业务规则。

## 总体架构

```text
草人杯菜单资源创意工坊 Addon
  ├─ 粒子、材质、纹理、图标
  └─ 最小测试地图与发布资料
          ↓
MultiAddonManager
  └─ 在任意当前地图上额外挂载资源并引导玩家下载
          ↓
CaorenCup 主插件的 ParticleMenu 功能模块
  ├─ 菜单会话与页面导航
  ├─ 粒子实体渲染
  ├─ 输入拦截与虚拟光标
  └─ 调用既有草人杯玩法功能
```

`ParticleMenuFeature` 是唯一入口，负责模块生命周期和事件注册。`ParticleMenuSession` 只保存某位玩家当前菜单的状态。渲染、输入、动作路由和清理分别独立，使任何一个页面或玩法动作都不需要直接操作其他模块的内部状态。

## 页面与业务动作

页面定义描述显示结构和允许的动作，不直接包含粒子实体操作。页面可以嵌套，但同一玩家任何时刻只保留当前页面的粒子实体。

允许的菜单项动作只有四类：

1. 打开子页面；
2. 返回上一页；
3. 调用现有草人杯功能；
4. 关闭菜单。

菜单会话维护一个页面返回栈。切换页面时先销毁旧页面实体，再创建新页面实体；不得在后台保留不可见的父页面。业务动作由 `ParticleMenuActionRouter` 映射到现有功能模块，菜单层不直接复制比赛或娱乐玩法逻辑。

## 输入状态与恢复

```text
关闭 → 打开 → 菜单活动 → 关闭等待左键松开 → 关闭
```

菜单活动期间：

- 锁定游戏视角；鼠标移动仅更新虚拟光标；
- 拦截攻击、副攻击、使用、切枪和其他配置为禁止的按键；
- 左键用于确认当前菜单项，并从游戏输入中清除攻击标记；
- 关闭时等待左键松开后才恢复攻击，防止点击关闭后误开枪。

玩家死亡、断线、换图、回合重置、插件卸载或任意菜单异常都必须调用同一个清理入口。清理顺序为：销毁页面粒子、取消输入拦截、恢复视角和移动限制、清空会话状态。

## 资源分发

菜单的 `.vpcf`、材质、纹理和图标编译后发布到草人杯专属创意工坊 Addon。服务器通过 MultiAddonManager 的服务器侧额外挂载模式使用该 Addon，使服务器可预载资源、客户端可自动下载资源。不得只把资源放入 CounterStrikeSharp 插件目录，也不得依赖玩家手动订阅。

由于此依赖位于 MetaMod 层，必须先在测试服验证创意工坊下载、资源预载、换图、玩家重连和插件卸载恢复，再考虑正式服部署。

## 性能预算与降级

- 每名玩家只允许一个活跃菜单页面。
- 页面切换必须释放旧页面实体。
- 虚拟光标仅在位置或命中项变化时更新，并限频；不得每 Tick 重建页面或广播菜单状态。
- 动态数据按配置的较低频率刷新；完整页面不应因单个数值变化而重建。
- 配置需定义：单玩家最大粒子实体数、单页最大项目数、最大页面层级、动态刷新间隔和关闭清理超时。
- 资源缺失、超过实体预算或渲染初始化失败时，显示普通文字备用菜单，并记录诊断日志。

## 验证

1. 使用原生粒子完成输入、锁视角、点击、返回栈与清理原型。
2. 发布小型自定义资源 Addon，通过 MultiAddonManager 验证未下载玩家的首次进入、已缓存玩家重连和官方地图换图。
3. 使用低配客户端，在静止菜单、连续移动光标、频繁切页和战斗/烟雾场景下记录平均 FPS 与 1% Low FPS。
4. 覆盖死亡、断线、换图、回合重置和异常关闭，确认没有残留粒子、输入锁或误开枪。
5. 仅在测试服通过后，按服务器部署流程单独部署实际变化的组件。

## 首个实现范围

首个实现只验证基础菜单能力，提供固定的“测试主菜单 → 测试子页面 → 返回/关闭”页面流，不接入赛事或娱乐玩法业务。菜单由仅管理员可用的测试命令打开。实际玩家入口、首批业务页面、视觉主题和创意工坊发布信息属于后续功能需求，必须分别设计并确认后才接入。

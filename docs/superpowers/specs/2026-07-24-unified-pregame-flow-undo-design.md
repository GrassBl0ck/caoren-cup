# 赛前统一撤销栈设计

## 目标

将主线已有的管理员赛前操作撤销，与新的阶段回退能力合并为一条后进先出的服务器内存历史。管理员既能撤销强制分队、强制 Ban 等同阶段操作，也能逐级回退手动、投票完成或倒计时触发的阶段推进；任何一次撤销都只恢复栈顶记录，避免两套历史互相覆盖。

## 历史模型

- 扩展现有 `FlowUndoManager`，不保留第二个独立的 `PhaseRollbackHistory`。
- 每条记录包含唯一 ID、操作类型、操作者、摘要、创建时间、恢复阶段和白名单快照。
- 阶段切换在产生副作用前建立快照，确认真正切换后入栈；失败或未发生的切换不留记录。
- 同阶段管理员操作继续在执行前建立快照，成功后保留，失败时丢弃。
- 历史只驻留于进程内存，最多保留 50 条；服务重启不导入历史。
- 进入 `LiveGame`、重开大厅、终止游戏和单挑自动退回大厅时清空历史。

## 快照与恢复

- 只保存赛前流程字段：阶段、队伍、队长、掷点、选人、地图池与 BP、地图/选边投票、身份分配、准备状态和其他赛前游戏字段。
- 不保存或恢复登录凭据、会员身份、在线/连接状态、管理员权限和玩家列表。
- 后加入的观战者继续保留。
- 快照依赖的参赛者缺失或已变成观战者时拒绝撤销，清空失效历史，并仅向操作者说明原因。
- 撤销前停止旧计时器。恢复到未完成的选人、地图投票或选边时重新给予完整倒计时并保留已有操作；已完成的阶段保持暂停，不立即自动推进。

## 权限与并发

- 正式管理员可撤销全部栈顶记录。
- 单挑临时管理员仅可撤销其单挑赛前推进产生的栈顶记录。
- 请求携带当前阶段、历史深度和栈顶记录 ID；服务端同时校验三者。重复点击或多人同时提交时，只有第一个有效请求能弹出记录。
- 撤销后再次操作会从当前状态建立新历史，不提供重做。

## 接口与界面

- 管理员专属状态沿用并扩展 `flowUndoStatus`，提供是否可撤销、历史深度、栈顶 ID、目标阶段、操作类型和安全摘要；普通玩家看不到这些字段。
- 管理员操作统一使用 `UNDO_FLOW_ACTION`，请求载荷包含 `expectedPhase`、`expectedHistoryDepth`、`expectedEntryId`。旧的无并发参数请求不再执行。
- 流程控制区只显示一个撤销按钮：阶段切换记录显示“回退到：阶段名”，同阶段操作显示“撤销：操作摘要”；单挑临时管理员面板使用同一状态与请求。
- 确认框说明当前阶段、目标阶段或待撤销操作，并提示之后产生的当前流程操作会被丢弃。
- 成功信息向所有玩家广播，具体失败原因只发送给操作者。

## 测试与验收

- 单元测试覆盖多级 LIFO、手动和自动推进、同阶段操作、快照白名单、身份与新观战者保留、依赖玩家缺失、计时恢复、清理时机和重复请求。
- 集成测试覆盖正式管理员、单挑临时管理员、投票/倒计时自动推进及 `Lobby → PreGameSetup → Lobby`。
- 静态前端检查验证按钮文案、确认提示、并发参数和单挑入口。
- 执行原阶段回退计划列出的全部测试，并补跑主线现有 `test:flow-undo`、公告、规则页和 JavaScript 语法检查。

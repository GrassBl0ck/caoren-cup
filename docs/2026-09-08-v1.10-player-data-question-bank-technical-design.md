## 2. 目标与非目标

### 2.1 目标

本设计建立可追溯、可审核、可发布、可复现的人物数据与题库计算底层，覆盖：

- 稳定人物 ID、HLTV 选手/教练 ID、别名和同名去重；
- HLTV 年度 Top 20 集合；
- 普通题库简单、普通、困难、专家四档累积集合；
- 普通题库“包含 Top 选手”开关；
- 榜单快照、战队成员时间段、Major 冠军阵容和个人贴纸；
- 人物准入证据、资格证据、数据版本、审核与发布；
- 与现有 `players`、`difficulty_levels` 和 `player_difficulties` 的兼容；
- 数据迁移、缓存、HTTP/内部 API 和测试边界。

### 2.2 非目标

本阶段不包含：

- HLTV、Valve 或第三方来源的实时联网抓取器；
- 完整比赛、地图和选手逐场统计数据库；
- 选择题状态机、判题、房间、观战和战绩实现；
- 玩家页面和管理页面的视觉实现；
- 生产数据库迁移、部署、Release、提交、推送、PR 或合并；
- 对原版猜选手玩法的题库规则重定义；
- ParticleMenu 和 Diagnostics。

人物的选手准入只保存“至少一场 HLTV 收录比赛”的最低证明。完整比赛历史留到第三批动态统计单独设计。

## 3. 现有实现调查

### 3.1 数据库与迁移

- 服务端使用 Knex，开发和测试支持 SQLite，生产配置要求 PostgreSQL。
- 当前 `ensureSchema()` 采用条件式建表和补列；应用启动只执行只读的 `assertDatabaseReady()`，DDL 由迁移命令负责。
- 当前没有有序迁移日志表。
- 当前本地 SQLite 数据库共有 5 名种子选手：`s1mple`、`ZywOo`、`device`、`NiKo`、`donk`。

### 3.2 现有人物模型

`players` 当前同时承担人物身份和原版猜选手资料：

- 主键为自增整数 `id`；
- `nickname` 全局唯一；
- 国籍、年龄等字段强制非空；
- `team_history` 是 JSON 文本；
- Major 冠军数和参赛数为汇总数字；
- 没有稳定跨环境人物 UID、别名、外部人物 ID、证据或事实版本。

`difficulty_levels` 当前只有：

- `beginner`
- `easy`
- `normal`

`player_difficulties` 是人物与上述旧难度的多对多关系。它被原版单人、多人、每日挑战、缓存、战绩和排行榜使用，不能改写为 1.10 新题库含义。

### 3.3 现有写入、缓存和接口

- 管理端和外部 Token 接口可以直接新增、修改、批量导入 `players`。
- 批量导入当前按昵称 upsert，无法安全处理同名人物。
- `player_change_submissions` 支持字段级审核，但批准后立即写入正式 `players`，并不是数据版本发布流程。
- `playerCache` 在进程内缓存全部启用人物、旧难度成员和公开列表，通过 Redis 修订号及 Pub/Sub 刷新。
- `resource:version` 是客户端资源更新通知，不是题库数据版本。
- 当前没有选择题或版本化题库实现。

## 4. 已确认的核心决策

1. 原版难度与 1.10 新题库分开保存，不复用或改写 `player_difficulties`。
2. 保留 `players.id` 作为旧外键；新增不可变 `person_uid` 作为跨环境和跨版本身份。
3. HLTV 选手 ID、教练 ID 和昵称都不是人物主键。
4. 正常数据自动校验，异常数据逐条人工复核，最终由管理员整版发布。
5. 旧人物数据保留原版兼容性，但未补齐公开证据前不自动取得新版题库资格。
6. 已发布数据版本不可原地修改；修正必须创建下一版本。
7. 运行中的对局锁定数据版本；发布或回滚不能改变已经开始的对局。
8. 本阶段只保存选手最低比赛准入证明，不导入完整比赛历史。

## 5. 总体架构

采用“增量式版本化模型”：保留现有表和旧玩法，在其旁边增加身份、证据、历史事实、候选审核、数据版本和物化题库成员。

服务端分为以下边界：

- `identity`：人物 UID、别名、外部身份和身份冲突；
- `evidence`：来源证据、导入批次和事实修订；
- `qualification`：纯规则计算，不依赖 HTTP、Redis 或随机数；
- `publication`：版本构建、校验、变化报告、发布和回滚；
- `questionBank`：读取指定版本的物化成员及题目安全事实；
- `questionBankCache`：进程缓存、Redis 通知和版本预热；
- 路由层：只负责鉴权、输入校验和响应映射。

数据流：

```text
来源记录
  → 导入批次与候选事实
  → 自动校验
  → 异常人工复核
  → 构建不可变数据版本快照
  → 计算资格与五个基础题库集合
  → 整版审核
  → 原子发布
  → 进程缓存与 Redis 通知
  → 对局锁定版本并出题
```

## 6. 人物身份模型

### 6.1 `players` 兼容扩展

保留现有 `players.id` 和全部历史外键，新增：

| 字段 | 说明 |
|---|---|
| `person_uid` | UUID 字符串，唯一、最终非空、创建后不可修改 |
| `merged_into_player_id` | 可空；误建重复人物被合并时指向保留人物 |
| `identity_status` | `candidate`、`verified`、`conflict`、`merged` |

规则：

- UUID 使用运行时自带的安全随机 UUID 生成能力，不根据昵称生成。
- `person_uid` 必须包含在新版导入导出和数据版本中。
- `players.id` 永不重新编号；已有游戏、每日挑战和多人回放外键不变。
- `is_enabled` 继续只表示能否进入原版猜选手缓存。
- 新题库成员资格不读取 `is_enabled`。
- 新数据版本只接受 `identity_status = verified` 且没有 `merged_into_player_id` 的人物；候选、冲突和已合并行不能进入 `U`。
- 取消 `nickname` 的全局唯一约束；不同人物允许同名。
- `players.nickname` 保留为当前主要显示昵称，并与主要别名同步。
- 年龄、国籍等字段允许为未知，但 `is_enabled=true` 的原版人物必须具备旧玩法所需的完整字段。
- 未知值保存为 `NULL`，不能使用 `0`、空字符串或虚构值代替。

### 6.2 `person_aliases`

建议字段：

- `id`
- `player_id`
- `alias`
- `normalized_alias`
- `alias_type`：`primary`、`former`、`transliteration`、`other`
- `valid_from`、`valid_to`
- `evidence_id`
- `created_at`

约束与行为：

- 同一人物的同一规范化别名不能重复。
- 不对 `normalized_alias` 建立跨人物唯一约束。
- 昵称、大小写、连字符或下划线相似只能用于查找候选，不能自动合并身份。
- 同名搜索结果必须附带国籍、身份、战队等版本化区分信息。

### 6.3 `person_external_identities`

建议字段：

- `id`
- `player_id`
- `source`：本阶段主要为 `hltv`
- `identity_type`：`player_profile` 或 `coach_profile`
- `external_id`
- `profile_url`
- `evidence_id`
- `verified_at`

唯一约束：

- `(source, identity_type, external_id)` 全局唯一；
- 同一个人物可以分别拥有一个 HLTV 选手档案和一个教练档案；
- 外部 ID 冲突时禁止覆盖，进入人工复核。

### 6.4 `person_career_roles`

记录人物在自然日区间内的身份：

- `player_id`
- `role_type`：`player` 或 `coach`
- `valid_from`、`valid_to`
- `evidence_id`

同一人物可以拥有连续或重叠的选手、教练身份。转任教练只新增事实，不创建第二个人物。

### 6.5 身份复核

`identity_review_cases` 至少包含：

- 冲突类型；
- 涉及人物、别名和外部身份；
- 严重级别；
- 当前状态；
- 处理决定、理由、操作人和时间。

导入阶段发现疑似重复时，先创建复核事项，不先创建第二条正式人物或静默绑定。已被历史记录引用的人物不得物理删除；误建重复人物通过 `merged_into_player_id` 保留审计关系。

## 7. 来源证据与历史事实

### 7.1 `source_evidence`

每条资格相关事实必须关联有效公开证据。建议字段：

- `id`
- `source_type`：`valve`、`hltv`、`other`
- `source_name`
- `source_record_key`
- `source_url`
- `evidence_date`
- `retrieved_at`
- `last_verified_at`
- `normalized_payload`
- `content_hash`
- `status`：`candidate`、`valid`、`invalid`、`conflict`

`evidence_date` 表示事实对应日期，`retrieved_at` 表示何时采集，两者不能混用。证据可以在截止日期以后被核验，但它证明的事实日期不能超出版本截止日期。

### 7.2 事实修订

所有候选事实表统一包含：

- 不可变事实修订 ID；
- `import_batch_id`；
- `evidence_id`；
- `supersedes_id`；
- 审核状态和审核记录；
- 创建时间。

已发布事实不更新原行。纠错时创建新修订并指向旧修订；不同数据版本可以分别保留新旧事实。

### 7.3 战队身份

新增：

- `teams`：稳定战队 UID、当前名称；
- `team_aliases`：历史名称、缩写和其他拼写；
- `team_external_identities`：HLTV、Valve 等来源中的战队 ID。

榜单和成员关系引用稳定战队 ID，不能按队名文本直接关联。

### 7.4 榜单快照

`ranking_snapshots`：

- 来源：`hltv` 或 `vrs`；
- 榜单范围：本期仅 `global`；
- 发布日期；
- 来源证据。

`ranking_entries`：

- `snapshot_id`
- `team_id`
- `rank`

约束：同一期名次不能重复，同一战队在同一期不能重复。

榜单有效期从发布日期开始，到下一期同来源、同范围榜单发布日期前结束。日期统一使用数据库 `date`，区间为 `[开始日期, 结束日期)`。最新一期最多计算到数据版本截止日期，不延伸到未来。

### 7.5 战队成员时间段

`team_memberships` 建议包含：

- `player_id`
- `team_id`
- `valid_from`、`valid_to`
- `member_role`：`player`、`registered_substitute`、`coach`
- `roster_status`：`active`、`benched`、`demoted`
- `contract_type`：`official`、`loan`、`trial`、`stand_in`
- `evidence_id`

排名资格只接受：

- `contract_type = official`；并且
- 正式选手、正式注册替补、板凳/下放正式成员或教练。

租借、试训和临时替补不能仅凭该时间段取得排名资格。

### 7.6 年度 Top 20

`annual_top_lists`：

- 年份；
- 状态：`published`、`officially_not_published`、`not_collected`；
- 来源证据。

`annual_top_entries`：

- `list_id`
- `player_id`
- `rank`（1～20）
- `evidence_id`

2012 年必须明确记录为 `officially_not_published`，不能与尚未采集混淆。

### 7.7 Major 与个人贴纸

新增：

- `majors`：赛事 UID、名称、开始/结束日期和证据；
- `major_team_results`：参赛战队和是否冠军；
- `major_roster_members`：人物、战队、身份和证据；
- `personal_stickers`：人物、Major、贴纸标识、是否个人签名及证据。

Major 冠军资格只接受冠军战队的正式选手、正式注册替补和教练。经理、领队、分析师、老板及其他工作人员不合格。个人贴纸资格只接受能对应具体人物的 Major 个人签名贴纸，队标贴纸不合格。

现有 `major_championships`、`major_appearances` 保留为原版兼容汇总字段；新版资格必须从明细计算，不能从汇总数字反推。

### 7.8 最低比赛准入证据

`person_match_evidence` 保存：

- `player_id`
- HLTV 比赛 ID 或记录标识；
- 比赛链接；
- 比赛日期；
- 游戏版本：`cs16`、`csgo`、`cs2`；
- `evidence_id`

一条有效记录即可证明人物满足“至少一场 HLTV 收录比赛”的选手准入条件。本阶段允许保存多条，但不要求完整比赛历史。

## 8. 数据版本与发布快照

### 8.1 `data_versions`

建议字段：

- `id`
- `version_uid`
- `display_version`
- `cutoff_date`
- `based_on_version_id`
- `status`：`draft`、`validating`、`in_review`、`published`、`rejected`
- `content_hash`
- `created_by_user_id`
- `reviewed_by_user_id`
- `published_by_user_id`
- `created_at`、`reviewed_at`、`published_at`

数据内容进入 `published` 后不可修改。版本状态和审计字段可以追加更新，但事实快照、资格结果和题库成员保持不可变。

### 8.2 版本事实快照

构建版本时，把被选中的已审核事实修订复制到带 `version_id` 的不可变快照表。至少包括：

- `version_person_facts`
- `version_person_external_identities`
- `version_team_memberships`
- `version_ranking_snapshots` 与 `version_ranking_entries`
- `version_annual_top_lists` 与 `version_annual_top_entries`
- `version_major_team_results` 与 `version_major_roster_members`
- `version_personal_stickers`
- `version_person_match_evidence`

`version_person_facts` 保存该版题目可以使用的当前昵称、真实姓名、国籍、出生日期、赛区、身份、状态和当前战队等。动态字段允许为空；题目模板只能使用自身要求的已验证字段。

“当前战队”“当前身份”和“当前状态”必须由截止日期当日有效的事实生成，不能直接复制采集时刻的可变文本。若同一截止日存在互相冲突的当前事实，该字段不进入快照并产生阻断级或警告级校验结果；系统不能任选其中一条。

年龄由出生日期和版本截止日期计算，不把持续变化的年龄作为新版事实来源。旧 `players.age` 只为原版兼容保留。

版本内容哈希由排序、规范化后的全部事实快照和题库成员共同计算，保证同一内容得到可核对的结果。

### 8.3 正式版本指针

`published_dataset_pointer` 每个发布通道只保存一个当前版本：

- `channel`：本期固定为 `default`
- `version_id`
- `updated_at`
- `updated_by_user_id`

发布或回滚在数据库事务内更新指针。旧版本不会被删除，运行中的对局继续引用原版本。

## 9. 资格与题库计算

### 9.1 资格结果

`qualification_results` 建议保存：

- `version_id`
- `player_id`
- `qualification_type`
- `first_qualified_on`
- `last_verified_at`

资格类型至少包括：

- `universe_player`
- `universe_coach`
- `annual_top20`
- `vrs_top10_membership`
- `major_champion_roster`
- `hltv_top20_membership`
- `major_personal_sticker`
- `hltv_top30_membership`

`qualification_evidence_links` 把每条资格结果关联到具体版本事实和来源证据。一个人物可因多条规则取得同一集合资格，管理端必须展示全部原因。

### 9.2 人物全集 `U`

满足任一条件：

1. 有有效 HLTV 选手档案，并且至少有一条有效 `person_match_evidence`；
2. 有有效 HLTV 教练档案。

同一人物同时命中两条时仍只计算一次。CS 1.6、CS:GO 和 CS2 比赛均有效。

### 9.3 Top 集合 `T`

汇总：

- 2010 年；
- 2011 年；
- 2013 年起所有已经正式发布的年度 Top 20。

同一人物多次入选只保留一次。2012 年不产生成员。若 Top 条目人物不属于 `U`，说明人物准入证据不完整，必须阻止发布。

### 9.4 时间重叠算法

排名资格要求榜单有效期与正式成员时间段至少重叠一个自然日。

```text
overlapStart = max(规则起算日, 榜单发布日期, 成员开始日)
overlapEnd   = min(下一期榜单发布日期, 成员结束日, 截止日期 + 1 日)

有效重叠条件：overlapStart < overlapEnd
```

未知结束日期视为开放区间，但仍受数据版本截止日期限制。成员开始/结束日期缺失或冲突时不能猜测，必须进入复核。

人物一旦在某个已选入版本的历史事实中取得资格，该资格在以后版本永久保留，除非证据被正式判定无效并通过新版本纠错。

### 9.5 原始难度集合

```text
S0 = VRS 前 10 合格成员
   ∪ Major 冠军合格阵容

N0 = S0
   ∪ HLTV 前 20 合格成员
   ∪ Major 个人签名贴纸人物

H0 = N0
   ∪ HLTV 前 30 合格成员

E0 = U
```

规则起算日期：

- VRS 前 10：2024-08-06；
- HLTV 前 20：2018-10-01；
- HLTV 前 30：2015-10-01。

所有原始集合最终与 `U` 取交集，避免无准入证据人物进入题库。

### 9.6 物化基础集合

`question_bank_memberships` 保存：

- `version_id`
- `pool_key`
- `player_id`

`pool_key` 固定为：

- `top`
- `regular_simple`
- `regular_normal`
- `regular_hard`
- `regular_expert`

计算公式：

```text
top             = T
regular_simple  = S0 - T
regular_normal  = N0 - T
regular_hard    = H0 - T
regular_expert  = U - T
```

显式保存五个集合，换取直接的查询、人数统计和审计。成员主键为 `(version_id, pool_key, player_id)`，同一集合中不能重复。

### 9.7 “包含 Top”

不物化额外组合：

```text
实际普通题库 = 所选 regular 集合 ∪ top
```

开启后加入全部 `T`，不要求 Top 人物命中当前普通难度自身规则。按 `player_id` 去重。

### 9.8 发布阻断校验

发布前必须满足：

- `T ⊆ U`；
- `regular_simple ⊆ regular_normal ⊆ regular_hard ⊆ regular_expert`；
- `top ∩ regular_expert = ∅`；
- `top ∪ regular_expert = U`；
- 所有成员拥有唯一稳定 UID；
- 每项资格至少关联一条有效证据；
- 没有未解决的阻断级身份、日期或来源冲突；
- 截止日期以后的事实未进入当前版本；
- 版本人数、集合哈希和变化报告已经生成。

## 10. 候选导入、审核与发布

### 10.1 导入批次

`data_import_batches` 保存：

- 来源；
- 导入文件哈希；
- 导入时间；
- 导入工具和规则版本；
- 提交人；
- 处理状态。

相同来源记录和内容哈希重复导入时保持幂等。外部 Token 只能提交候选数据，不能审核或发布。

### 10.2 校验结果

`data_validation_findings` 保存规则编号、严重级别、涉及对象、说明、处理状态和处理记录。

严重级别：

- `info`：普通统计或无需处理的信息；
- `warning`：允许带说明发布，但必须出现在变化报告；
- `blocking`：处理前禁止发布。

外部 ID 冲突、同名身份不明、日期倒置、排名重复、成员时间段矛盾和资格证据缺失属于阻断项。

`data_admin_audit_log` 独立记录人物合并、证据裁决、版本审核、发布和回滚。审计记录至少包含操作类型、对象、操作前后摘要、原因、操作人、时间和请求幂等标识，且普通管理接口不能修改或删除。

### 10.3 审核策略

- 来源明确、结构校验通过且人物身份唯一的事实可以自动进入候选版本。
- 异常数据逐条人工复核。
- 管理员最终批准完整版本，而不是逐条批准全部正常历史数据。
- 所有自动判断仍保留来源和规则执行记录。

### 10.4 变化报告

发布前至少展示：

- 人物新增、停用和合并数量；
- Top 和四档普通题库人数；
- 相比上一版本新增、移除和资格变化的人物；
- 各资格规则命中数量；
- 缺少不同题目字段的人数；
- 全部阻断项和未解决警告；
- 证据抽样结果。

### 10.5 发布与回滚

发布步骤：

1. 从上一正式版本创建草稿；
2. 选择已审核事实修订并创建不可变快照；
3. 计算资格和题库成员；
4. 运行阻断校验；
5. 管理员复核变化报告；
6. 在事务中锁定版本并切换正式指针；
7. 事务提交后预热缓存并广播新版本。

回滚只把正式指针切换到某个已发布旧版本，必须记录原因、管理员和时间，不删除或修改任何版本。

## 11. 缓存设计

### 11.1 缓存内容

进程内缓存保存：

- 当前正式版本元数据；
- 指定版本五个基础集合的成员 ID；
- 该版本题目安全的人物事实快照；
- 各组合人数。

Redis 保存：

- 当前正式版本提示；
- 版本修订号；
- 发布通知频道；
- 可选的版本成员集合副本。

数据库始终是事实来源，Redis 只负责加速和跨实例通知。

### 11.2 缓存键

所有缓存键包含 `version_uid`，例如：

```text
question-bank:version:<uid>:top
question-bank:version:<uid>:regular:simple
question-bank:version:<uid>:regular:normal
question-bank:version:<uid>:regular:hard
question-bank:version:<uid>:regular:expert
```

旧版本数据不可变，因此不做主动内容失效；使用容量上限和过期时间逐步清理。存在进行中对局引用的版本必须能从数据库重建。

### 11.3 发布一致性

- 发布事务提交后再发送 Redis 通知，不能提前广播未提交版本。
- 收到通知的实例核对数据库正式指针后再切换。
- 每次开始新对局都核对正式版本，避免只依赖可能丢失的通知。
- Redis 不可用时直接读取数据库并填充进程缓存。
- Redis 通知失败不回滚已经成功的数据库发布，但必须记录告警。
- 数据库中没有可用正式版本时禁止开始新局，不能退回草稿或空集合。

### 11.4 “包含 Top”缓存

只缓存五个基础集合。“包含 Top”在内存中对所选普通集合和 Top 集合求去重并集，不长期保存四份重复组合。

## 12. API 设计

### 12.1 内部领域接口

所有题目生成器必须调用统一接口，不能自行拼接题库 SQL：

```ts
resolveQuestionBankPool({
  versionUid,
  bank: 'top' | 'regular',
  difficulty: 'simple' | 'normal' | 'hard' | 'expert' | null,
  includeTop: boolean,
})
```

约束：

- `bank = top` 时，`difficulty` 必须为 `null`，`includeTop` 必须为 `false`；
- `bank = regular` 时必须指定难度；
- 返回固定版本、截止日期、实际成员集合和人数；
- 无效组合返回结构化错误，不自动修正请求。

新难度键故意使用 `simple`，不复用原版 `easy` 的语义；两者处于不同模型和接口边界。

### 12.2 玩家 API

`GET /api/question-bank/catalog` 返回：

- 当前正式 `versionUid`；
- 数据截止日期；
- 可选题库和难度；
- 各组合实际人数；
- 当前是否允许开始。

不返回：

- 草稿或审核状态；
- 资格证据和管理备注；
- 完整人物集合；
- 正确答案或题目生成内部字段。

此处人数表示符合题库成员规则的唯一人物数量，不代表某一批题目模板能够生成的唯一题目数量。选择题开局容量由后续题目模板与状态机设计基于同一版本另行计算。

开局请求只提交 `bank`、`difficulty` 和 `includeTop`。服务端读取当时正式版本、完成校验并把 `version_uid` 写入对局。客户端不能指定任意草稿版本。重连时继续使用对局已经锁定的版本。

### 12.3 管理 API

管理接口分组提供：

- 人物、别名、外部身份和身份复核；
- 来源证据、导入批次和事实修订；
- 数据版本、校验结果和变化报告；
- 人物资格解释；
- 构建、提交审核、发布和回滚。

发布和回滚要求：

- 管理员身份；
- 请求携带预期当前版本，执行乐观并发检查；
- 操作原因；
- 幂等请求标识，防止重复点击造成二次执行。

### 12.4 旧接口兼容

- 现有 `/players` 管理、外部导入和 `player_change_submissions` 继续维护原版资料。
- 旧接口写入不会自动创建新版资格或发布数据版本。
- 单条更新继续使用数字 `players.id`。
- 新版导入导出包含 `personUid`，导入优先按它匹配。
- 仅有昵称的旧格式只有在恰好匹配一人时才能更新；匹配多人时返回身份不明确错误。
- 新建人物自动生成 UID，但保持候选状态。
- 现有 `resource:version` 继续只用于客户端资源通知；题库使用独立正式版本指针和 Redis 命名空间。

## 13. 数据迁移设计

### 13.1 迁移框架

新增 `schema_migrations` 和按编号执行的迁移文件。现有 `ensureSchema()` 继续负责旧基础结构，不在本阶段整体重写；新复杂变更进入有序迁移。

每条迁移记录：

- 迁移编号和名称；
- 内容校验值；
- 开始和完成时间；
- 执行结果。

迁移必须支持 SQLite 和 PostgreSQL，并在应用启动前由迁移命令完成。

### 13.2 迁移步骤

1. 创建迁移日志及所有新增表；
2. 给 `players` 增加可空 `person_uid` 等兼容列；
3. 为现有人物逐行生成并持久化一次性 UID；
4. 把现有昵称写入主要别名；
5. 校验 UID 和别名回填结果；
6. 增加 UID 唯一和非空约束；
7. 放宽新人物可能未知的旧资料字段；
8. 移除昵称全局唯一约束；
9. 添加原版启用人物完整性校验；
10. 更新旧导入、搜索和变更审核的歧义处理；
11. 更新数据库就绪检查；
12. 验证原版缓存和历史外键不变。

迁移不会自动创建正式 1.10 题库版本。现有记录只成为待补证候选。

### 13.3 SQLite 特殊处理

SQLite 取消表级唯一约束和改变部分列约束时需要重建 `players`：

1. 在事务中创建新表；
2. 按原 `id` 复制数据；
3. 核对总行数、每个 ID 和关键字段；
4. 重建索引及外键；
5. 运行外键检查；
6. 全部通过后替换旧表；
7. 任一检查失败回滚事务。

不能先删除旧表再进行无保护的数据修复。

### 13.4 备份与回滚边界

实际实施前必须：

- 备份 SQLite 文件或 PostgreSQL 数据库；
- 备份不得加入 Git；
- 先在备份副本上完整演练；
- 记录迁移前行数、旧难度成员和历史外键摘要。

应用层回滚优先恢复旧程序并使用迁移前备份。本设计不承诺对已经写入新版数据的复杂表执行自动降级迁移。

## 15. 失败处理原则

- 身份、来源、日期和资格冲突保存为结构化校验结果，不能只写日志。
- 阻断错误禁止发布；警告必须进入变化报告。
- 发布事务失败时正式指针保持不变。
- Redis 故障不改变数据库事实。
- 缓存缺失可以重建；正式版本缺失不能伪装为空题库。
- 导入、计算和发布必须幂等，重复请求不能产生重复资格或重复版本切换。
- 删除或禁用人物前检查旧游戏、新版快照、资格、题目和对局引用。
- 已发布或被历史记录引用的人物只能停用或合并，不能物理删除。

## 16. 分阶段实施边界

后续实施计划应按依赖顺序拆分：

1. 有序迁移框架和人物 UID 兼容迁移；
2. 人物别名、外部身份、证据和身份复核；
3. 战队、榜单、成员时间段、Top、Major、贴纸和比赛准入事实；
4. 数据版本快照和纯资格计算器；
5. 物化题库、集合校验和变化报告；
6. 审核发布、回滚、缓存和 API；
7. SQLite/PostgreSQL/Redis 集成测试及原版回归。

每阶段实施前仍需按项目规范备份相关文件，不得将备份加入 Git。完成本底层不等于完整选择题玩法完成；选择题状态机、模板和前端需要后续独立设计与实施。
